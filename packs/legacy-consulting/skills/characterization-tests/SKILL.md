# characterization-tests

你是負責舊系統替換的工程師。這個 skill 的前提是：**舊系統的行為就是規格**，不管它合不合理。
你的工作不是判斷它對不對，是把它固定下來，讓之後任何改動都有東西可比。

## 什麼時候不要用

- 舊系統的行為本來就要改（那是 spec-kit 的事，不是這裡）
- 輸出每次都不一樣又沒辦法固定（時間戳、隨機數）且找不到可以 mask 的方法
- 沒有辦法在隔離環境執行舊系統

遇到以上情況，停下來跟使用者講，不要硬做。

## 原則

1. **先找邊界，再找案例。** 邊界是「輸入進去、輸出出來」的地方：一支 API、一個批次、一張報表、一個 CLI。從 `inventory/report.md` 與 `specs/` 找出這次要替換的那幾個邊界，每個邊界一組測試。
2. **案例來自真實資料，不是你編的。** 從 `.grill/` 訪談紀錄找「正常」「月底」「例外」三類案例；有 DB 唯讀帳號就抽真實紀錄（紅級資料先去識別化）。自己編的案例會漏掉舊系統真正在處理的怪狀況。
3. **錄下來的就是答案。** 第一次跑把輸出存成 golden file，不要檢查內容。看起來很怪的輸出也存，另外寫進「待確認」。
4. **穩定化只做最少。** 時間戳、自增 ID、浮點尾數用 mask 或正規化處理；每多一條 mask 規則就註解它為什麼存在。
5. **一個邊界一個目錄。** `tests/characterization/<邊界名>/`，裡面是 `cases/`（輸入）、`golden/`（錄到的輸出）、一支跑測試的腳本。語言跟新系統一致。
6. **跑兩次才算錄好。** 同樣輸入連跑兩次輸出相同，才能進 golden。不同就代表還有沒 mask 的東西。

## 流程

```
1. 列邊界     ← 從 inventory/report.md 與 specs/<feature>/spec.md
2. 收案例     ← .grill/、DB 抽樣、既有測試資料；每個邊界至少「正常 / 邊界值 / 例外」各一
3. 寫 harness ← 能對舊系統下輸入、收輸出的最薄一層
4. 錄 golden  ← 跑兩次確認穩定
5. 寫 README  ← 每個邊界：案例來源、mask 規則與理由、待確認的怪輸出
6. 接進 CI 或 check.sh，新系統實作時以此為驗收
```

## 輸出

`tests/characterization/README.md`：

```markdown
# 行為封存：<系統 / 模組>
- 錄製日期：
- 舊系統版本 / 環境：
- 邊界數：N，案例數：M

## 邊界
| 邊界 | 類型 | 案例數 | 案例來源 | mask 規則 |
|---|---|---|---|---|
| 出貨單產生 | 批次 | 12 | .grill/2026-..-shipping.md、DB 抽樣 | 時間戳、單號 |

## 待確認（錄到但看起來不對的輸出）
- <邊界> case <n>：<現象>。可能是 bug 也可能是潛規則，請問 <角色>。

## 怎麼跑
<指令>
```

「待確認」的每一條都轉給 `inventory-gaps`，變成下一輪訪談題目。

## 不要做的事

- 不要「順便修」舊系統的 bug。錄下來，另外報。
- 不要用新系統的輸出當 golden。那是在考自己出的題。
- 不要為了讓測試穩定而 mask 掉有業務意義的欄位（金額、數量、狀態）。
- 不要把含真實個資的 golden file 交出去或進雲端 agent；紅級資料在錄製前去識別化。
